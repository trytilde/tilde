## v5.10.0 - 2026-11-27
### Changed

* chat-ui: Chat shows messages, tool calls and reasoning in the order they happened, live and after a reload (within the recent activity a reload replays). Only consecutive tool calls share a block. Reasoning splits where a message or tool call comes between.
* Linear setup lists numbered steps for its OAuth app and API key; the setup page shows the OAuth redirect URL with a copy button; and connections with a webhook set up in the hosted page, which shows the webhook URL to copy.

## v5.9.0 - 2026-11-26
### Added
* Sandbox egress reaches the API providers agents read from sandboxes, with the connection's credential added at the gateway: Linear (GraphQL queries and the granted mutations), Sentry (reads and issue updates, narrowed to organizations), Jira (API token connections), PagerDuty, Datadog, Grafana, Prometheus, New Relic, Honeycomb, HCP Terraform, and AWS, whose requests the gateway signs with SigV4 for the service and region the sandbox's SDK signed for, limited to the grant's services, regions and reads. Each provider's standard client is wired to the route (`LINEAR_API_URL`, `SENTRY_URL`, `AWS_ENDPOINT_URL` with the egress token as the access key ID, `DD_API_KEY`, `GRAFANA_URL`, `HONEYCOMB_API_ENDPOINT`...), every grant also sets `TILDE_EGRESS_<SLUG>_TOKEN`, and the route takes the token wherever those clients send their key.
* Every framework adapter suspends and resumes its loop with no change to agent code: the Vercel AI SDK (`prepareTildeCall`), Mastra (`tildeMastra`), LangChain (`tildeMiddleware`) and OpenAI Agents (`tildeOpenAIAgents`) in TypeScript, and LangChain, OpenAI Agents and Pydantic AI in Python, save the conversation in their framework's message format before the next model call when a Tilde tool call answers pending or Tilde's deadline comes, and continue from it with the call's outcome in the run's next invocation. The contract is on `AgentContext` (`enableSuspension`/`enable_suspension`, `shouldSuspend`, `suspend`, `resumed`). Agno and CrewAI cannot replace their loop's messages at a step boundary and keep blocking calls.
* Runs outlive their invocations: a tool call of a caller that can suspend (the SDKs' framework adapters) that is still running after a minute (`TILDE_TOOL_PENDING_AFTER_MS`), or at the invocation's deadline, answers pending and goes on in the background; the adapter saves its conversation with `ChatService.SuspendRun` and the invocation ends; once the pending calls finish Tilde starts the same run's next invocation (`InvokeRequest.resumes`), which reads the state and the outcomes with `GetCheckpoint`. Tilde owns the runtime limit: a Lambda invocation is asked to suspend two minutes before Lambda's fifteen (the control stream's suspend command, which now leaves the stream open until the invocation ends). The built-in `thread.wait_for_reply` (thread.read) waits for a person the same way: its output is the next message routed to the agent, which then starts no run of its own.
### Changed

* Built-in tool definitions (`tools::builtin::definition`) are shared across the engine, so tool providers outside the tools module (Tilde Cloud's `user.link_identity`, which links a chat account to a signed-in person) describe their tools the same way.

## v5.8.0 - 2026-11-26
### Added
* Built-in skill and wiki-link tools: `skills.write` (create or replace a skill in an editor skill source, offered with `skills.edit`), `skills.assign` and `skills.unassign` (give or take a skill source or one skill, offered with `agents.edit_skills`; assigning also needs `skills.read` on the source) and `wiki.link` / `wiki.unlink` (give another agent a wiki the calling agent is linked to, read or read-write up to its own access, or take it away), offered with the new capability `agents.edit_wikis`, which the agent editor, `tilde.types.v1.Capabilities` and declarative apply (`capabilities` in `@trytilde/iac`) carry. Each authorizes like the runtime or management call it mirrors. `agents.list` now returns each agent's `key`.
* `tilde build [ENTRY] [--agent <key>] [--out <dir>] [--version <v>]` builds an agent's deployable artifacts exactly as `tilde deploy` builds them, without deploying: `declarations.json` (the code's DeploymentDeclarations), `agent.json` (the agent's spec as Apply receives it), a Hosted agent's `bundle.zip` and, with `--version`, `manifest.json` (`{ version, sha256, declarations }`). It contacts no Tilde server and needs no credentials. A Hosted bundle is now reproducible: entries in path order with a fixed time, so the same sources give the same digest.
### Changed

* A connection in use can no longer be disconnected: `ConnectionsService.Disconnect` (and deleting a tool host whose instances are in use) refuses with `failed_precondition` naming every use (agent assignments, personal allowances, tool sources, routines, sandbox blueprints and egress grants, sandboxes left on an old connection, memory embeddings and synthesis), and `Connection.usages` lists them on GetConnection and ListConnections, shown as "In use by" in the console where the Disconnect action is now blocked. A disconnected connection cannot be assigned, used as a tool source or by a routine until it is reconnected, and foreign keys from those uses now restrict deletes instead of silently unbinding them. Deleting an agent also removes its tool sources, routines (with their run history) and personal allowances.
* Chat agent discovery is ConnectRPC. `@trytilde/chat-ui` lists the agents through `ChatService/ListAgents` at the proxy itself (`<proxy>/tilde.provider.tilde.v1.ChatService/ListAgents`), and `@trytilde/chat-proxy` (with `@trytilde/chat-next`) and the Python `create_chat_proxy` serve it there, in the caller's codec (Connect's JSON or binary), for every configured agent the user may chat with. `GET <proxy>/agents` is gone: update chat-ui and the proxy together. AGENTS.md now says ConnectRPC is for every API we design, and plain HTTP only for third-party webhooks, OAuth/OIDC, OTLP, protocol passthrough proxies, pages and static assets, and health checks.

## v5.6.0 - 2026-11-25
### Added
* Hosted deployments (Tilde Cloud): `deploy: { target: "hosted" }` in `@trytilde/iac`, or `tilde deploy --target hosted`, has Tilde run the agent's code itself. `tilde deploy` bundles the code with esbuild (`dist/index.mjs` exporting `handler`, with `prompts/` and `skills/`) and publishes it once the deployment is registered (`DeploymentService/PublishHostedDeployment`; an open-source server refuses it). A blueprint spec names its sandbox `connection` (it was `provider`) like any connection reference; on Tilde Cloud every team has the Tilde sandbox connection `tilde_sandbox/sandbox`, whose blueprints run `debian-node`, `debian-python` or `debian-full`.
* `@trytilde/chat-ui`: `Chat.fetch` replaces the cookie-carrying fetch for agent discovery and every ChatService call, so a host can send a bearer token instead (Tilde Cloud spaces' `<AgentChat>`) or answer from fixtures in tests and Storybook.
* `@trytilde/iac`: `lambda(functionArn, role)` names the IAM role Tilde assumes to invoke a Lambda deployment (`targetRole`). Tilde Cloud requires it and assumes it with the organization's ID as the external ID.
* One theme for every embedded UI: `@trytilde/chat-ui`'s `Chat`, `ListSessions` and `Transcript` take `theme` (the `Theme` that `@trytilde/embed` gives a space) and derive their palette from its tokens, with `scheme` choosing light or dark without a `.dark` ancestor; `@trytilde/embed`'s `mountConnectionSetup({ theme })` (plus `setTheme`) and `<ConnectionSetup theme>` style Tilde's setup page, including provider pages built on `useSetup`. The type now lives in `@trytilde/sdk/theme`; Tilde's own setup dialog follows the app's light or dark.
* `@trytilde/chat-ui`'s `Chat` (also `@trytilde/embed/react`'s) takes `header={false}` to show only the transcript and the message bar. The chat pane no longer draws a right border, and its hover washes (message actions, header actions, the attach button and its menu rows) come from the palette's `--hover`, which a theme derives from `ink`, instead of a fixed grey.
* Ten more built-in connection providers for the software factory, each with tools for agents: GitLab (access token on gitlab.com or a self-managed URL, or an OAuth app), Jira Cloud (API token or OAuth 2.0 3LO), Entire (service account secret and cluster host), Datadog, Grafana, Prometheus, PagerDuty (API key or OAuth), New Relic, Honeycomb and Terraform (HCP Terraform or Terraform Enterprise). GitLab and Entire are git forges with sandbox egress like GitHub: a blueprint's grant narrows to projects or repositories and push branches (default `factory/*`), sandboxes clone and push through the gateway (`entire://` remotes included, with no remote helper), and the credential never enters the VM. Atlassian, GitLab, Datadog, New Relic and Honeycomb's hosted MCP servers join the same providers as `mcp_oauth` types. `@trytilde/iac` has typed refs for all ten (`gitlab.ref(...).tools(...)`).
* `tilde deploy` (Tilde Cloud ontologies): a first deploy creates the ontology's project (in the deploy's team) and each environment the organization does not have yet, instead of asking for them to be created by hand; the plan lists what it creates. `@trytilde/iac`: an ontology environment takes `live` (`environments: { production: { live: true } }`), set when the deploy creates the environment.
### Changed

* Ontology slots are connections: `defineProject({ ontologies: { <name>: ontology({ environments: { <env>: { connections, secrets } } }) } })` replaces `slots`, `ontology<typeof connections>()` types the bindings by the ontology's own `connections`, and `tilde deploy`'s plan says `connection <name>`.
* `tilde deploy` prints deployment tokens only for dial-in hosts (gateway, sidecar): a Lambda or Hosted deployment's token is never printed.
* `tilde deploy` bundles a Hosted agent's linked prompt and skill files with their content, and refuses a linked folder (or names a broken link) in `prompts/` or `skills/` with a clear message.
* `tilde deploy` and `@trytilde/iac` send and read only `name`/`connections`: they need Tilde Cloud with the connections rename, and `slots` is no longer read.
* `@trytilde/chat-ui`: a refused proxy request shows its Connect error message instead of "Sign in to chat" or "Unable to load agents"; `ListSessions` takes `fetch` like `Chat` (both must be stable or memoised); a viewer who is not yet in the thread posts naming no participant, for the server to bind (Tilde Cloud spaces join the viewer on their first post).
* The sandbox egress route checks and forwards a request's path as the client sent it, still percent-encoded, instead of decoding it first: an encoded slash (`%2F`) in a GitHub REST path is now refused rather than read as a path separator. Escapes of unreserved characters are decoded before the rules are checked, so escaping a letter of a denied path (`%61ctions/secrets`) does not sidestep the rule, and a `%` that starts no escape is refused.
* `tilde deploy` (Tilde Cloud ontologies): a connection the ontology declares optional (`{ provider, optional: true }` in its `connections`) no longer has to be bound or in the spec; the deploy reports it as skipped and rolls out without it. `--check` on an ontology whose project does not exist yet is refused: Tilde compiles an ontology for its project, which the first deploy creates.

## v5.5.0 - 2026-11-23
### Added
* A project's root `tilde deploy` releases every agent that declares `deploy`, after its ontologies and their bindings. Each agent's code is in `agents/<key>/`, or wherever `defineAgent({ code })` names (an entry module, or a folder with its own package.json or pyproject.toml); `tilde deploy` reads each one's prompts, skills and tools there and registers a deployment with an external ID of its own. An agent with neither has its code in another repository: its spec is applied, it is not released, and a note says so. From an agent's own folder, the one deploying agent without code of its own releases the entry's declarations, so `tilde deploy` there works as before. A deploy with several deploying agents prints each new dial-in token as a `<key> <token>` line; with one, the token alone. `--check` no longer reads the agents' code.
* Declarative apply sets an agent's chat channels: an agent spec's `channels` assigns channel connections (Slack, Google Chat and the rest) and sets each channel's access mode, the agent's own Tilde chat included. Preflight lists a missing channel connection with a link, and refuses one another agent has. A channel the spec leaves out stays; `delete` unassigns one.
### Changed

* An existing `agents/<key>/` folder without its own package.json or pyproject.toml now fails `tilde deploy` with an error naming the folder, instead of being read as part of the project around it.
* `@trytilde/iac` connection refs accept names with spaces (`google_chat/Google Chat`), as the app lets people name connections; a name still cannot start or end with one.
* An agent folder may hold its own `tilde.config.ts`: the agent's release, like `tilde dev`, reads the package's code entry (`main`, `dist/index.js`, ...), never the config.
* `tilde deploy` from an agent's own folder releases that agent's code: when the folder is the agent's own (named after its key, or under `agents/`), its `tilde.config.ts` declares only that agent and its package's code entry exists, that package is its code. A config-only repo declaring one remote agent still applies its spec without a release. `tilde dev`'s fallback command runs the package's code, never its `tilde.config.ts`.
* Declarative apply of channels: tightening a channel's access stops the runs it no longer allows, a new channel starts in its provider's own mode (GitHub's is disabled) so a repeat changes nothing, an unsupported mode or two agents claiming one connection are required actions before anything is written, and deleting a channel another agent has is a no-op.
### Removed
* `tilde.toml` is gone. The CLI finds a project's `tilde.config.ts` at its root; agents' code comes from `agents/<key>/` or `defineAgent({ code })`; a project without a config keeps its package's conventions for its entry (`main`, then `dist/index.js`, then `src/index.ts`; Python's `src/agent.py` and so on), and `--entry` still overrides it. Ontology projects are named by their key in `defineProject({ ontologies })`, and `tilde dev` starts an agent with its package's `dev` or `start` script.

## v5.4.2 - 2026-11-23
### Added
* Memory's own model calls now show up in inference usage. Background embedding and recall from the console count as the organization's spend. A recall query an agent's memory tool embeds counts toward that agent's usage and budgets. Synthesis calls are billed to their memory bank. The embedding settings and each bank's synthesis panel show this month's spend. Rows in `inference_requests` may now have no agent or invocation, and carry `memory_bank_id` for synthesis.
### Changed

* A new project deploys its ontologies and agents in one `tilde deploy`. Before the ontologies first roll out, Tilde lists none of their tools, so the agents' preflight used to block on every tool named on an ontology's connection (`tilde_ontology/...`) and the first deploy needed `--only ontologies`. Those tools are now checked against the compiled contract (what CompileOntology returns), in `tilde deploy`, `--dry-run` and `--check` alike: a tool the ontologies don't serve still blocks before anything changes. The Apply after the rollout checks them against the running ontology as before.
* `tilde deploy --ontology` naming every ontology of the project checks the agents' ontology tools against the compiled contract, as a deploy without `--ontology` does. Only a selection that leaves an ontology out has nothing to check them against.

## v5.4.1 - 2026-11-23
### Added
* `tilde deploy --check` builds a project's ontologies as a deploy would (evaluates each, has Tilde compile it, bundles its handler module and builds its spaces against the returned contract) and stops: nothing is uploaded or changed, and the working tree may be dirty. It needs only the npm packages and Tilde's compile RPC, so a project's CI can check its ontology without any server-side binary.
### Changed

* Modal blueprint sandboxes pick up a moved image tag. The launcher resolves the blueprint image's tag to its digest at the registry and builds `FROM <image>@sha256:…`, so Modal's image cache, which keys on the `FROM` line, builds again when `:latest` moves instead of running whatever it built first. If the registry can't be reached, it builds from the tag and logs a warning. E2B blueprints launch a template's latest build already.

## v5.4.0 - 2026-11-23
### Changed

* `tilde deploy --dry-run` shows each ontology slot binding that changes as `slot: current → new`, and counts the unchanged ones.
* `tilde deploy` builds a project's ontologies on the client and uploads artifacts: each ontology's IR, evaluated with the project's own `@trytilde/ontology` (install it beside each ontology, and `@trytilde/spaces` in its spaces) and checked by Tilde Cloud (`CompileOntology`, whose errors fail the deploy before anything changes), its handler module and its spaces, built against the contract Tilde compiles. ## v5.3.0 - 2026-11-22
### Added
* `@trytilde/iac`: agent configuration in code (`defineAgent`, `defineProject`, `connection.ref`, `blueprint`, `egress`, `routine`, `lambda`/`gateway`/`sidecar`), with typed catalog providers (`github.ref("acme").tools("github_get_issue")`) whose tool names are string-literal unions generated from the built-in catalog, `ALL` (`"*"`) and `.untypedTools()` for anything else. `tilde deploy` applies the specs an entry exports in one `ApplyService.Apply` call, prints the plan or every required action with its link, supports `--dry-run`, `--json` and `--team`, and exits 2 when blocked; entries without specs register their deployment as before.
* `@trytilde/iac`: `secret.ref("NAME")` references a secret set in Tilde (Connections → Secrets) from a sandbox blueprint's environment; the value never enters the spec, and `tilde deploy` prints a link that adds a missing one.
* `@trytilde/iac`: people in code for Tilde Cloud: `defineTeam({ team, users, groups })`, `user()` and `group()` (declared with an object, referenced by email or name), users and groups beside an agent, and `access: [grant(group("eng"), "ownership")]`; users upsert their name, `login: true | { role }` sets the team role and invites, `team: { delete: true }` leaves the team, and `delete: true` disables a user or deletes a group. `tilde deploy` sends them with the agents, or alone for a team-only project.
* SDKs: `serve({ run })` (TypeScript) and `serve(run=...)` (Python) host an agent wherever its entry module runs: inside AWS Lambda it is the Lambda handler (`export const handler = serve({ run })`), with a deployment token it connects a dial-in host, and on a plain import (or while `tilde deploy` reads the module) it does nothing, replacing the Lambda-or-dial-in branch in entry modules.
* `tilde iac types` writes a `.d.ts` from the organization's own connections (MCP servers and tool hosts' instances): it augments `@trytilde/iac`'s new `Connections` interface, so `connection.ref("acme_mcp/prod")` takes that connection's type and tool names and a typo does not compile. Slugs it does not list, and `untypedTools`, still take plain strings.
* `tilde local`: connect a harness on your machine to a local agent, an agent Tilde lists and equips but never runs. `tilde local install claude-code|codex|claude-desktop --url <gateway> --agent-id <id>` stores the agent's key in `~/.tilde/local`, adds the harness's hooks and registers `tilde local mcp` as its MCP server, so the agent's tools reach the harness without the key entering its configuration. The hooks report each Claude Code and Codex session to Tilde as a thread (prompts, answers and finished tool calls, sent once and resumed from a cursor) and keep the agent's skills in the harness's own skill folder; `tilde local uninstall` removes all of it. Contracts: `Agent.local` (harness and the features its adapter supports), `CreateAgentRequest.harness` and `tilde.local.v1.LocalAgentService`.
* Chat and signal providers: Google Chat as a chat provider; Linear connections with tools and issue/comment signals; Sentry regression and alert signals; CloudWatch alarm signals through SNS on AWS connections; and filters on signal routines.
* AWS connections reach other accounts through assumed roles (assume_role_arns, external_id, an account_id argument on every AWS tool and aws_list_accounts), and a new oidc connection type federates with Tilde's own OpenID Connect issuer (ENGINE_TOKEN_ISSUER_URL, discovery and JWKS under /oidc) instead of access keys.
* Native chat: an application's user lists the providers an agent may use for them, connects their own account on Tilde's hosted setup page, and lists, reconnects or removes their connections (`ChatService` `ListConnectableProviders`, `StartConnection`, `ListConnections`, `ReconnectConnection`, `DeleteConnection`), for the agent's personal tools in their conversations. Owners choose which agents may use their personal connections (every agent granted `tools.personal` for the provider, the default, or only listed agents), enforced in the invocation catalog and on every call; personal tool calls record the connection they ran on.
* Sandbox egress on the server: blueprints grant sandboxes a connection's upstream through the gateway at `/sandboxes/egress/{slug}/…` with a minted credential that never enters the VM. Connection types gain the `egress` capability (GitHub App, personal access token and OAuth connections first); SetBlueprintEgress and DeleteBlueprintEgress manage a blueprint's grants, whose config only narrows the provider's rules; git fetch and push (granted branches only, never deletes, rewrites or the default branch) and a small REST allowlist are checked, and every request is traced on the sandbox's invocation. The blueprint page gets an Egress section.
* Declarative apply on the server: `ApplyService.Apply` makes the registry match agent specs written in code (agent, inference aliases, tool sources, sandbox blueprint with environment and egress, routines and the already-deployed deployment) in one transaction, upserting by key and removing only entries marked `delete`; preflight lists every required action first and a dry run returns the plan. Secrets (Connections → Secrets, `SecretService`) keep named, write-only values that a sandbox blueprint's environment can reference, read when a sandbox process connects.
* Local agents: an agent that runs in a harness on a person's machine (Claude Code, Codex, Claude Desktop, ChatGPT Desktop) is registered with `CreateAgent`'s `harness` (Agent Registry → Connect local agent). Tilde never runs it; its harness reports sessions through `tilde.local.v1.LocalAgentService` (one thread per session, every event a span) and reads the agent's skills, and `/agents/{agent}/mcp` serves the agent's tools as an MCP server.
* Tilde runs in a schema of its own beside another application's tables: with `options=-c search_path=<schema>,public` on `DATABASE_URL`, migrations create the schema when it is missing. `DATABASE_DIRECT_URL` optionally names the server behind a transaction-pooling PgBouncer `DATABASE_URL`, used only for migrations and the one LISTEN session per process.
* `@trytilde/iac`: `defineProject({ ontologies: { <name>: ontology({ environments: { <env>: { slots, secrets } } }) } })` declares a project's ontologies (Tilde Cloud, each in the repository's `ontologies/<name>/`) and each environment's connection slot and secret bindings; `ontology<typeof slots>()` types a slot's binding by its provider (`ConnectionRef` now carries `provider`). `tilde deploy` deploys them before the agents, changing nothing until everything is checked (the ontologies' preflight and the agents' dry-run Apply, every missing project, environment, connection and secret with a link): then a version per ontology from the repository at HEAD, checked against the spec, and each environment bound and rolled out in turn (`--only ontologies|agents`, `--ontology <name>`, `--allow-dirty`, `--accept-rebuild <model>`). A server without ontologies answers that they need Tilde Cloud.
### Changed

* Registry pages live under `/registry` (agents, skills, tools, sandboxes, memory and wikis); `/` opens the registry. The Connections page splits connections by what they are for (Tools & chat, Inference & embedding, Sandboxes, and Other) above the source tabs, and adds inference and sandbox connections from their tab. Memory facts and wiki pages are edited in a rich Markdown editor.
* Connections mint the credentials consumers send upstream through one service: a stored credential as it is, or GitHub App installation tokens and AWS STS sessions, cached until shortly before they expire. Health probes are no longer traced, unmatched routes are traced only on a 5xx, and ENGINE_CLICKHOUSE_CA_CERT pins a self-hosted ClickHouse's CA.
* Sidecar-hosted agents get their tool sources, not just channel tools. Agent heartbeats no longer queue behind other notifying commits on a busy Postgres. AWS SigV4 signing encodes the canonical path for every service but S3, so Lambda wakes are accepted. Web errors no longer start with the RPC code, and a missing agent links back to the registry.

## v5.2.0 - 2026-11-20
### Added
* Sandbox images to try Tilde sandboxes with: `ghcr.io/trytilde/sandbox-debian-node`, `sandbox-debian-python` and `sandbox-debian-full` (both, plus Docker Engine and Docker Compose). Each is Debian with the `tilde` CLI of the same release and common agent tools (git, gh, jq, ripgrep, fd, build tools), and is tagged with the release version.
### Changed

* The TypeScript and Python SDKs call tools over `ChatService/InvokeToolStream`, which streams heartbeats while the tool runs, so tool calls longer than a proxy's idle timeout (such as 60 s behind a load balancer) no longer fail.
* Long calls survive proxies with idle timeouts (an AWS load balancer cuts a connection silent for 60 s). `ChatService.InvokeToolStream` and `SandboxService.InvokeToolStream` stream a heartbeat every 10 s while a tool runs, then the result (`tilde sandbox call` uses it, falling back to `InvokeTool`); sidecars relay over `SidecarService.RelayStream`, bounded by 45 s of silence instead of 15 s in all; `WatchThread` sends a keepalive frame (no activity, same cursor); a non-streamed inference call silent for 20 s is answered 200 with JSON whitespace until the provider's body. Management RPCs waiting on outside work fail after 45 s with their own error, or finish skill source syncs in the background. `InvokeTool` and `Relay` remain for older SDKs and sidecars.

## v3.0.0 - 2026-09-30
### Added
* Support agent sidecars that cache conversations in memory beside the agent process and execute the threads they hold a lease on, taking the lease in the same gateway call that hydrates a thread and paying no per-event gateway calls afterwards; they dial the gateway over one connection for configuration, leases, projection and forwarding, and relay traces and logs through the gateway. The gateway serves every route group on one listener selected by ENGINE_SERVE.
* Collect agent OTel logs through Rotel into ClickHouse, independently forward to external collectors, and browse correlated logs in the agent Logs tab.
* Register agent deployments from CI or the UI with per-deployment tokens, route new threads to the serving deployment and pin existing ones, and record each invocation's deployment so instances, failover and history stay scoped to it.
* Wake-and-dial run protocol. Long-running hosts dial the gateway with their deployment token and receive wakes as frames, Lambda deployments are woken through the AWS invoke API, and every host reports acceptance, reasoning and completion through RunService with its invocation capability; the SDK gains connectAgent and createLambdaHandler.
* Sidecar agents dial their sidecar over the run protocol with the deployment token, so the HTTP endpoint map and health probe become optional fallbacks; sidecars leave gracefully by releasing idle leases and reporting themselves gone, and keep cached conversations within a per-agent byte budget.
* Preserve agent queue, interrupt and batch policies across gateway and sidecar runtimes; add provider sending identities, typed SDK history and channel tools, the Vercel AI SDK adapter, and automatic local example-agent startup.
* Inference gateway that forwards agents' provider SDK traffic (OpenAI, Anthropic, Azure OpenAI, Azure AI, Google AI Studio, Bedrock, Baseten, Cerebras, Vercel AI Gateway, Cohere, Voyage) by connection slug with the invocation token, swaps credentials from memory on gateway and sidecar, accounts usage off the request path, and warms channel tools, credentials and first-page history when an invocation starts.
* Inference cost tracking priced from a vendored LiteLLM price sheet at insert time, agent and identity budgets (day, month or total; block or flag) settled by a worker and enforced through the invocation token's inference claim on gateway and sidecar, and a management InferenceService for usage and budgets.
* Add framework adapters for LangChain/LangGraph, OpenAI Agents and Mastra to the TypeScript SDK with example agents, and a Python SDK workspace (`trytilde` core with the ConnectRPC agent host, FastAPI mounting and chat proxy, plus `trytilde-langchain`, `trytilde-pydantic-ai`, `trytilde-openai-agents`, `trytilde-agno` and `trytilde-crewai` adapters with example agents). `REGISTER_DEV_AGENTS=1 task dev` now registers and starts one example agent per adapter, filtered by `DEV_AGENTS`.
* Accept gzip-compressed Connect request bodies on every listener, including the chat provider ingress and sidecar relay paths that read the body before the Connect handler; the Python SDK no longer disables request compression.
* Tilde stores agent traces, logs and metrics itself. Agents upload OTLP to /v1/traces, /v1/logs and /v1/metrics on the gateway or their sidecar. Batches are queued in object storage (ENGINE_TRACES_S3_BUCKET, ENGINE_LOGS_S3_BUCKET, ENGINE_METRICS_S3_BUCKET) with a pointer in Postgres, so gateways are stateless and any replica delivers what another accepted; each queue bucket needs a lifecycle rule of at least a day. Batches are stored in ClickHouse (ENGINE_CLICKHOUSE_*, retention set by ENGINE_CLICKHOUSE_RETENTION_DAYS, unset keeps everything) and can also be forwarded to any OTLP/HTTP collector (TRACES_OTLP_*, LOGS_OTLP_*, METRICS_OTLP_*). The Tracing, Sessions and Logs tabs read them through the management API under a mandatory agent scope, with search by name, type, level, model, session, invocation, input and output text, numeric comparisons and any span attribute. Generation spans are priced from the inference price table. Base64 media and payloads over 64 KiB move to ENGINE_MEDIA_S3_BUCKET and are rendered in the inspector.
* Prompt management and agent skills. `tilde deploy` (TypeScript and Python SDKs) registers a deployment together with the prompts and skills its code declares, read from the agent framework's own objects (Mastra, Vercel AI SDK and eve, LangChain, OpenAI Agents, CrewAI, Pydantic AI, Agno) or from definePrompt/defineSkills; prompt versions are content-hashed in plain, mustache, braces or dynamic form, the inference gateway links every call to the versions that produced it so cost, tokens and latency compare per version, and the Prompts and Deployments tabs show history, diffs, usage and what each deployment shipped. Bundled skills are pinned per deployment and private to their agent; registry skills reach every deployment live through each framework's own skill mechanism. Skills are grouped into skill sources (Tilde catalog groups, GitHub repositories synced hourly and on request, or editor collections) with a Skills page; files live content-addressed in ENGINE_SKILLS_S3_BUCKET. Agents are given whole sources, single skills, or the skills linked to a connection through its new skills capability, and read them through ctx.skills; the skills.edit capability lets an agent author into and sync the sources it targets. The agents.edit_skills capability unlocks runtime skill management on the targeted agents.
* Agents use tools Tilde manages. On an agent's Tools tab you add a tool connection or a tool server, pick which of its tools the agent uses and which run in the background, and choose whether they are listed or found by search; agents see them as `source.tool`. Tools come from managed providers (Google Workspace, GitHub, Slack, Sentry, PostHog, Firecrawl, Stripe, Payload, Tavily, Linq, AgentMail, WhatsApp, E2B, Modal, AWS), 23 curated MCP servers, MCP servers added by URL (with dynamic OAuth client registration), and customer tool servers that dial in or run on Lambda, optionally with credentialed instances. The Tools area lists connections, a browsable catalog and remote servers.
* Agents declare bundled tools, shipped in their code and run in their process, the way their framework already defines tools, and hand them to the adapter's `withTildeTools` (TypeScript) or `with_tilde_tools` (Python), which returns the framework's own tools. Their descriptions, summaries, schemas and hints are published on every invocation, so tool search describes them beside Tilde's tools and the agent's Tools tab lists them read-only, and each call is recorded with its summary. The Python SDK gains tool summaries, annotations, output schemas and `ctx.tool_source`. Traces show the tool `tools.execute` ran beneath it and cover a background tool's work until it finishes.
* Agents have a description, shown and edited inline under the agent's name. The agents home page has a filter bar: search matches names and descriptions, and agents can be filtered by health (healthy, degraded, unhealthy, unknown) and by whether they are paused. Filtering happens on the server, so every page of results is filtered.
* `tilde deploy` declares an agent's bundled tools with the deployment: native framework tools in a `defineTools` / `define_tools` value exported from the entry, and the static tools of recognised framework agents, described exactly as `withTildeTools` / `with_tilde_tools` publishes them. `GetDeploymentContents` returns them and `--dry-run` prints them.
### Changed
* Version the Rust binary and TypeScript SDK packages together using Changie.

* Deliver steering, cancellation and suspension through execution-owned control subscriptions. Support Node serverless handlers and remove inbound host control RPCs and synchronous pause acknowledgements.
* Generated TypeScript contracts move into the @trytilde/contracts package, built from the protos on demand and no longer committed; the web app and SDK import from it instead of carrying duplicate copies.
* Sidecar publishes project lease releases in queue order, the projection checks thread membership on every event, Lambda deployments can serve gateway agents, routing enforces the pinned deployment, hosts report failed runs, hydration restores goals, tasks, conversions and run origins, a draining or fenced sidecar stops its agent process through the command stream, and the liveness window is one constant.
* Move native chat to the Tilde ConnectRPC provider with encrypted API keys, identity-scoped access, session search/read state and queue controls; add embeddable React chat, a server proxy and Next.js routes.
* The built-in Tilde chat provider is now a catalog provider like the others: every agent owns one system-managed Tilde connection, created with the agent, whose application key is the connection's credential. Its access mode and asserted identities live where every other provider keeps them, so the agent's access tab lists it beside the connections with public, private or disabled modes (private by default) and per-identity allow switches, with no provider-specific handling; identities asserted by the application are recorded on first contact and can be added ahead of time. The access tab also refreshes when it is opened so providers added moments earlier appear without a reload. Agent settings tabs moved to a row under the breadcrumb, and provider setup failures are logged with the provider's reason.
* Releases run automatically when a release PR's version lands on main. They publish the container image to GHCR (`ghcr.io/trytilde/tilde`), every public `@trytilde/*` npm package and the Python SDK packages to PyPI through trusted publishing, and attach the packages to the GitHub release; native binary archives are no longer published. Release preparation bumps the Python SDK lockfile with its manifests and accepts an explicit version. Encryption contexts and the container user are named `tilde`.
### Removed
* Remove every gateway-to-agent and sidecar-to-agent HTTP call. Agent hosts only dial in (`connectAgent` / `connect_agent`) and receive wakes as `RunService.Watch` frames; the `AgentService` Invoke/Healthz contract, `createAgentServer`/`createAgentHandler`, wake signatures, agent endpoint URLs, webhook signing keys, the sidecar HTTP fallback (`ENGINE_SIDECAR_AGENT_ENDPOINTS`) and HTTP health probes are gone. Sidecar replicas no longer call each other: work for a conversation held elsewhere goes through the gateway. Agent creation no longer creates a deployment; readiness comes from heartbeats.
